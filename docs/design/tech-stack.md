## 7. 选型理由

### 7.1 为什么选 Spring Cloud + Vue3？

| 考量 | 选择 | 理由 |
|------|------|------|
| 团队能力 | Java + Vue | 国内景区/文旅行业主流技术栈，招聘市场供给充足 |
| 生态成熟度 | Spring Cloud Alibaba | 与阿里云基础设施深度集成（Nacos、Sentinel、RocketMQ） |
| 甲方要求 | Java + MySQL | 甲方倾向可维护性强的主流技术栈 |
| 跨端需求 | uni-app (Vue3) | 一套代码覆盖小程序 + H5 + App，降低多端维护成本 |
| 性能 | Spring Boot 3.x + 虚拟线程 | JDK 21 虚拟线程支持高并发 I/O 场景 |

### 7.2 为什么 MySQL 而不是 PostgreSQL？

- MySQL 8.0 足以满足 OLTP 场景需求
- 运维团队 MySQL 运维经验更丰富
- 阿里云 MySQL 高可用版成熟度更高

### 7.3 为什么 RabbitMQ 而不是 Kafka？

- 业务场景以异步解耦、削峰填谷为主，RabbitMQ 足够
- RabbitMQ 延迟队列、死信队列等特性更适合订单超时取消等场景
- 运维复杂度低于 Kafka

### 7.4 为什么不选微服务全套 Spring Cloud？

| 场景 | 调整 |
|------|------|
| BFF 层 | Node.js (NestJS) 替代 Spring Boot，利用 JS 同构优势 |
| 数据脚本 | Python 替代 Java，开发效率更高 |

## 8. 版本管理

| 组件 | 版本策略 |
|------|----------|
| JDK | LTS 版本 21，非 LTS 不用于生产 |
| Spring Boot / Cloud | 跟随 Spring 官方发布节奏，延迟 1 个小版本升级 |
| MySQL | 仅使用 GA 版本，升级前充分验证兼容性 |
| Redis | 跟随稳定版，跨大版本升级前压测 |
| 前端依赖 | 锁定小版本 (package-lock.json)，定期 `npm audit` |
